# Сервер Entrixy — установка на свой сервер

Здесь всё, что нужно, чтобы поднять собственный сервер Entrixy: веб-часть,
вебсокет-воркер, база и TLS. Это не урезанная версия и не демонстрация —
функционал полный: объекты, гостевые ключи, передача по цепочке, отзыв,
журнал, сокет-контроллеры, лимиты. Ставьте для себя или для своих клиентов,
приложение переключается на ваш сервер в настройках.

Мимо вашего сервера у приложения остаётся ровно один канал — к entrixy.com за
обновлением самого приложения, отчётом о сбое и объявлениями. Открытия, ключи
и объекты туда не ходят вовсе.

## Что нужно

Любая машина с Docker и git и домен, указывающий на неё А-записью. Сертификат
выпускается автоматически, вручную ничего настраивать не надо.

## Установка

    git clone https://github.com/entrixy/server.git entrixy-server
    cd entrixy-server
    cp .env.example .env
    nano .env                      # домен, пароли базы, секреты
    docker compose up -d --build

Первый запуск занимает несколько минут: собираются образы и наливается схема
базы. Контейнеры слушают только петлевой адрес: веб на `127.0.0.1:8082`,
вебсокет на `127.0.0.1:8095`.

Два значения в `.env` не придумывают, а генерируют:

    openssl rand -hex 32           # JWT_SECRET

Пароли базы — любые, наружу они не уходят. В `APP_ATTEST_SECRET` уже стоит
значение, совпадающее с приложением из магазина: оставьте как есть, если не
собираете приложение сами.

### После первого запуска

Три проверки по порядку. Первая говорит, что веб-часть поднялась и база на
месте:

    curl -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8082/key

Ждём `200`. Дальше, когда домен уже проксируется, страница должна открыться
с оформлением и значком вкладки — если она голая, статику перехватывает
панель, что делать, сказано ниже. И вебсокет, у которого своя ловушка:

    python3 tools/ws_check.py wss://ваш-домен/ws     # ждём 101 и pong

Из коробки дверь открыта: любое приложение, которому назвали ваш адрес,
заведёт устройство. Так задумано — серверу для себя большего обычно не надо.
Если он поднят для круга людей, закройте его кодом или приглашениями прежде,
чем раздавать адрес: раздел «Сервер только для своих».

## Как отдать сервер наружу

**Если на машине уже работает nginx** — а так обычно и бывает на сервере с
чужими сайтами, — порты 80 и 443 остаются за ним. Заведите поддомен и выпустите
сертификат штатными средствами панели, а затем добавьте проксирование. Образцов
два, и выбор между ними важен:

* `nginx-entrixy.conf.example` — для nginx, который вы правите руками: целый
  блок `server` со своим сертификатом;
* `nginx-entrixy-panel.conf.example` — для панели (Hestia, ISPmanager). Там
  включаемый файл подставляется внутрь готового блока `server`, где `location /`
  уже занят панелью, поэтому корень объявлен регуляркой `location ~ ^/`, а `/ws`
  — префиксом `location ^~ /ws`, который эту регулярку перебивает. Целый
  `server {}` в такой файл класть нельзя: nginx откажется с `duplicate location`.

Боевые конфиги при этом не трогаются вовсе.

**Если машина чистая**, сервер умеет держать TLS сам:

    docker compose --profile tls up -d --build

Тогда поднимается Caddy, занимает 80 и 443 и выпускает сертификат для домена
из `DOMAIN` без ручной настройки.

### Когда статику перехватывает панель

Это ловушка, которая стоит дороже всего времени. Собственный конфиг панели
обычно заканчивается регуляркой на статические расширения — css, js, png, ico
и прочие, — и такие файлы она отдаёт из своего каталога. Ваших там нет, они
внутри контейнера: страницы поднимаются, а стили и иконки отвечают 404 —
голая страница без оформления и пустой значок вкладки.

Префиксные блоки в образце закрывают каталоги, а точные блоки `location = ` —
файлы, лежащие в корне: `assets.css`, три значка, `apple-touch-icon.png` и
`robots.txt`. Оба вида стоят там именно поэтому. Точное совпадение в nginx
побеждает любую регулярку независимо от порядка подключения, префикс с `^~`
побеждает её тоже — на этом образец и работает, не требуя правок в конфиге
самой панели.

Если вы пишете конфиг сами и файл всё равно отвечает 404, проверьте его так:

    curl -I https://ваш-домен/assets.css

Ответ 404 с заголовком сервера панели означает, что запрос до контейнера не
дошёл: добавьте для этого файла `location = `, как в образце.

### Ошибки и то, что видит посетитель

Ошибки PHP уходят в журнал контейнера и никогда в ответ: предупреждение,
показанное посетителю, печатает абсолютные пути и устройство кода. Версия по
той же причине убрана из заголовков ответа. И то и другое задано в образе,
настраивать нечего.

Исходники вебсокет-воркера при сборке удаляются из веб-контейнера — он
работает в своём и по HTTP сказать ему нечего. Правила адресов отказывают
`/w/` тоже: это на случай собранного вручную образа.

Увидели ошибку PHP в браузере — значит перед вами образ, собранный до этой
правки: пересоберите `git pull && docker compose up -d --build`.

### Про файрвол

Docker умеет дописывать свои правила в iptables и обходить существующие. Здесь
этого не происходит: порты публикуются на `127.0.0.1`, а не на всех адресах,
поэтому снаружи контейнеры не видны и защита машины их не касается. Менять
`HTTP_BIND` на `0.0.0.0` без нужды не стоит — сервер и так доступен через
прокси.

## Переключить приложение

В приложении: «Настройки» → адрес сервера → ваш домен. Гостевые ссылки,
выданные с этого сервера, ведут на него же: гость, открывший такую ссылку,
подключается к вашему серверу автоматически.

Приложение работает с несколькими серверами сразу: ключи, выданные соседями и
управляющей компанией с других серверов, продолжают действовать, а новые
объекты заводятся на том сервере, что выбран в настройках.

Одна настройка при этом важна. Ключи, помеченные владельцем как «только для
приложения», приложение подписывает секретом, зашитым в его сборку. Сервер
проверяет подпись тем же секретом, поэтому в `.env` он должен совпадать со
сборкой, к которой вы подключаетесь. Для приложения из магазина это

    APP_ATTEST_SECRET=eNtR1xy_App_Att3st_2026_9f4Kq2Lm7Xb!

Значение не тайна: оно лежит внутри установочного файла и вынимается
разбором. Собираете приложение сами — ставьте в обе стороны своё. Поставите
разное — такие ключи перестанут открывать, обычные продолжат работать.

## Что внутри

| Сервис | Что делает |
|---|---|
| `caddy` | сертификат, порты 80 и 443, адрес `/ws` уходит в воркер |
| `web` | Apache и PHP: запросы приложения, страница гостевого ключа |
| `ws` | вебсокет-воркер: живые соединения с телефонами и платами |
| `db` | MariaDB, данные лежат в томе `db_data` |

Веб-часть и воркер общаются только через базу, поэтому перезапуск любого из
них другой переживает спокойно.

## Обновление

    git pull
    docker compose up -d --build

Ваш `.env` остаётся на месте — он не отслеживается. Схема базы догоняется
сама: при старте веб-часть сверяет базу с той схемой, что пришла с кодом, и
добавляет недостающие таблицы, столбцы и индексы. В журнале видно, что именно
добавилось:

    docker compose logs web | tail

Добавляет она только новое и никогда ничего не удаляет: столбец, оставшийся
от прошлой версии, вреда не приносит, а данные из удалённого не вернуть. Если
выпуск потребует переделать существующий столбец, об этом будет сказано в
описании выпуска отдельно.

Данные при обновлении остаются на месте: они лежат в томе `db_data`, а образы
пересобираются рядом.

## Чего этот сервер не делает

Не шлёт писем: почтовой части здесь нет вовсе — см. «Учётные записи и почта».

Не собирает прошивки в браузере. Для этого нужны наши сборочные машины, и это
остаётся на entrixy.com; сами контроллеры с вашим сервером работают как
обычно.

Пуш-уведомления отправляет только после того, как вы дадите свой проект
Firebase и свою сборку приложения — почему и как, в следующем разделе.

К открытию по Bluetooth не имеет отношения вовсе: оно работает от телефона к
контроллеру независимо от того, поднят сервер или нет.

Две вещи уходят к нам, а не к вам, и ни в одной нет ни открытий, ни ключей, ни
объектов: приложение обновляется из магазина и отправляет на entrixy.com отчёты
о сбоях и объявления. По той же причине страница гостевого ключа ведёт на наш
адрес за установкой приложения и за браузерным клиентом — в `dist/key.php`
рядом с этими ссылками стоят комментарии, где и что заменить, если хотите
держать их у себя.

## Пуш-уведомления

Без них сервер работает: пока приложение держит соединение, вызов от гостя
доходит сразу. Пуш нужен для случая, когда соединение оборвалось — телефон
спал, сеть моргнула, система выгрузила приложение.

Отправлять пуш умеет любой сервер, а вот доставить его конкретному телефону
может только тот, чей проект Firebase зашит в это приложение. У приложения из
магазина проект наш, и вашим ключом до него не достучаться. Поэтому пуши на
своём сервере — это связка из двух вещей: ваш проект Firebase и ваша сборка
приложения с его `google-services.json`. Исходники приложения мы выкладываем
отдельно.

Когда проект заведён, возьмите в его настройках ключ служебной учётной записи
(Project settings → Service accounts → Generate new private key), положите
файл рядом:

    secrets/fcm-service-account.json

и поднимите сервер заново. Каталог `secrets/` уже подключён к контейнерам
только на чтение, менять ничего не нужно. Файл не подхватился — в журнале
будет видно, а уведомления просто останутся такими же, как без него.

## Учётные записи и почта

Писем сервер не шлёт совсем: почтовой части в дистрибутиве нет. Вместе с ней
не приехали страница входа и регистрация — это наш сайт, а не сервер.

Устройству учётная запись не нужна: приложение регистрируется само и работает
без всякого входа, лимиты берутся из строки `default` таблицы `plans`. Если вы
захотите привязывать устройства к людям — скажем, чтобы лимиты переживали
переустановку приложения, — заводите записи в таблице `users` тем способом,
который вам удобен, и привязывайте устройство обращением `host_account`. Как
при этом подтверждать почту и восстанавливать пароль, решать вам: в этой части
мы вам ничего не навязываем.

## Компании на вашем сервере

Раздел компаний работает и здесь: организация регистрируется, выкладывает у
себя на домене `/.well-known/entrixy.json` с открытым ключом и подписывает им
каждое обращение. Ваш сервер эти подписи проверяет и сохраняет.

Важно, как устроено доверие. Домен проверяет сервер, а не приложение, и это
сделано ради клиента: если бы за ключом ходил телефон, компания видела бы его
адрес и точный момент проверки — то есть «этот человек прямо сейчас решает,
давать ли мне доступ». Ходит сервер, и компания видит только его.

Платой за это стало то, что значок подлинности читается как «проверено
Entrixy»: приложение рисует логотип и выделенный домен только для записей с
entrixy.com. На вашем сервере компании работают полностью — регистрация,
обращения, ключи, отзыв, — но в приложении показываются названием, без знаков
подлинности. Иначе любой сервер мог бы выдать себя за известную компанию, а
проверить это человеку нечем.

## Пределы обращений

Предел есть у каждой точки входа, и ставится он в момент прихода запроса, а не
точка за точкой: что бы новая точка ни забыла объявить, пол под ней уже есть.
Этот пол — `REQUESTS_PER_MIN`, число обращений с одного адреса к одной точке за
минуту, по умолчанию 300.

Чувствительные места держатся строже прямо в коде, и настройка их не касается:
регистрация устройства — пять в минуту, привязка контроллера — двадцать,
выдача ключа — тридцать. Открытие ограничено отдельно, по ключу, настройкой
`RATE_LIMIT_PER_MIN`.

Без нужды пол не занижайте. За одним адресом оператора сидят тысячи абонентов,
и жёсткое число отрежет соседей вместе с тем, кого вы хотели остановить. Счёт
идёт в памяти веб-контейнера, поэтому перезапуск его обнуляет — и это
свойство, а не недостаток: пределы существуют, чтобы ограничить поток, а не
чтобы кого-то наказывать.

Сверх предела сервер отвечает 429 с полем `retry_after`, и приложение само
выжидает это время.

## Сервер только для своих

По умолчанию сервер открыт: любое приложение, которому назвали ваш адрес,
заведёт на нём устройство. Данных это не выдаёт — объекты и ключи зашифрованы,
и чужое устройство видит ровно ничего, — но место в вашей базе занимает.
Закрыть вход можно двумя способами, и выбор между ними зависит от того, для
кого сервер.

### Сервер для себя: общий код

    ACCESS_CODE=любая_строка_подлиннее

Устройство заводится, только если приложение прислало тот же код. Код один на
всех и едет вместе с адресом, поэтому отсекает он улицу, а не знакомых: кто
код узнал, тот и вошёл. Для домашнего сервера этого достаточно.

### Сервер для клиентов: приглашения

Приглашение — код на одно устройство, со сроком годности и пометкой, кому
выдан. Регистрация его гасит, поэтому подсмотренное приглашение бесполезно:
оно уже использовано. Набить сервер чужими устройствами по одному коду тоже
не выйдет — каждому нужен свой.

    docker compose exec web entrixy-invites add --count 5 --days 30 --note "Иванов"

Команда печатает готовые строки вида `5wvv7qbu6cdx@gate.example.com`. Такую
строку целиком и выдают человеку: он вставляет её в поле адреса сервера, а
приложение само отделит код от адреса. Никаких отдельных полей заполнять не
нужно.

    docker compose exec web entrixy-invites list

показывает выданные приглашения: сколько раз ещё можно войти, до какого числа
и сколько устройств по нему завелось.

    docker compose exec web entrixy-invites revoke 5wvv7qbu6cdx

закрывает приглашение на будущее. Устройства, заведённые по нему раньше,
продолжают работать — так задумано: обычно код отзывают потому, что он
разошёлся, а не потому, что человек стал нежеланным. Если нежеланным стал
именно человек, добавьте `--with-devices`: тогда его устройства удалятся
вместе со всем, что они успели завести. Команда сначала скажет, сколько их, и
спросит подтверждение — отменить это потом нельзя.

Первое же созданное приглашение закрывает сервер: с этого момента устройство
заводится либо по общему коду, либо по действующему приглашению. Отозвали все
приглашения и не задали общий код — сервер снова открыт.

### Чего код не делает

Он решает, кто войдёт, и только. Внутри всё как обычно: лимиты берутся из
`plans`, гостя с выданным ключом код не касается вовсе — доступ ему даёт сам
ключ. Чужих данных это тоже не трогает: даже вошедший видит только своё,
соседние записи для него нечитаемы.

## Лимиты и тарифы

Из коробки телефон регистрируется безымянно: сервер выдаёт устройству пару
удостоверений и считает лимиты по нему самому. Умолчание — **20 объектов и
20 гостевых ключей** на устройство, строка `default` в таблице `plans`.
Меняются они прямо там:

    UPDATE plans SET max_numbers = 50, max_keys = 100 WHERE name = 'default';

Ни в приложении, ни в прошивке числа не зашиты: сервер присылает их при
синхронизации, приложение показывает и по ним же отказывает в добавлении.

### Куда подключаются свои тарифы

В сервере оставлено место под учёт по людям, а не по устройствам.

* приложение может прислать при регистрации токен входа — поле `account_token`
  в `api/register_host.php`;
* устройство цепляется к человеку — столбец `hosts.user_id`;
* лимиты тогда берутся из тарифа человека — `users.plan_id` → `plans`, вся
  логика в `lib/account.php`, функция `account_limits()`;
* привязать или отвязать уже зарегистрированный телефон — `api/host_account.php`.

Пример второго тарифа лежит в той же таблице строкой `account`. Заведите свои
строки и раздайте их людям через `users.plan_id` — этого достаточно, чтобы
разные люди получали разные лимиты.

Дальше — ваша территория. Кто такие пользователи, как они платят, что показывать
в кабинете, как продлевать подписку: всё это ваш сервер и ваши правила. Механизм
рабочий и полный, схему оплаты и интерфейс поверх него мы не диктуем.

На ключи аккаунт не влияет никак: они шифруются на телефоне, и сервер не видит
их ни с аккаунтом, ни без него.

## Адрес сервера в контроллерах

Контроллер идёт на тот адрес, который зашит в его программу при сборке. По
умолчанию сборщик подставляет адрес того сервера, с которого собирают, так что
прошивка, собранная у вас, к вам же и подключится. Явно адрес задаётся полем
`ws_host` (и `ws_port`) в запросе к `api/esp_compile.php` — в интерфейсе
конфигуратора этого поля нет намеренно, чтобы обычный человек не увёл свой
контроллер на чужую машину случайным нажатием.

В прошивке адрес лежит константой `WS_HOST`, в скриптах для Raspberry и Node —
строкой `WS_URL`. Если собираете прошивки своим способом, меняйте их там.

## Сборка без интернета

Исходники apcu лежат в самом репозитории (`vendor/`), никаких внешних хостов сборка
не опрашивает, кроме репозиториев Debian и реестра образов. На машине, где
ходить наружу можно только через зеркала, этого достаточно.

## Если сборка падает

**`apt-get update` не может разрешить имена.** Так бывает на Ubuntu 24.04 и
других системах с systemd-resolved: контейнерам нельзя отдать адрес
`127.0.0.53`, и Docker подставляет шлюз, который запросы не обслуживает.
Лечится явными серверами имён:

    cat > /etc/docker/daemon.json <<'JSON'
    { "dns": ["1.1.1.1", "8.8.8.8"] }
    JSON
    systemctl restart docker

**Обычные контейнеры имена уже разрешают, а сборка всё равно падает.** У
нового сборщика своя сеть, настройки демона он не читает. Собирайте старым:

    DOCKER_BUILDKIT=0 docker compose up -d --build

## Проверка вебсокета

Только клиентом по HTTP/1.1 — это важно. Через nginx домен отдаётся по HTTP/2,
а в нём заголовки `Upgrade` и `Connection` запрещены, так что апгрейд
невозможен в принципе. И `curl`, и `websocat` по TLS договариваются на HTTP/2
сами, и исправно настроенный сервер выглядит сломанным. В комплекте лежит
клиент, который этой ловушки лишён:

    python3 tools/ws_check.py wss://ваш-домен/ws     # ждём 101 и pong
    python3 tools/ws_check.py ws://127.0.0.1:8095/ws # то же без прокси

Тем же curl проверять можно, но с явным `--http1.1`.

### Ответ 101 без заголовка Upgrade

Воркер отвечает на рукопожатие заголовком `Upgrade: websocket`. Некоторые
панели прячут заголовки ответа, и до клиента он не доходит. Браузер и
приложение по стандарту такое рукопожатие отвергают и переподключаются
бесконечно, при том что страницы и API работают, — со стороны это выглядит
бедой приложения, а не прокси. В журнале приложения это видно как

    Expected 'Upgrade' header value 'websocket' but was 'null'

`tools/ws_check.py` об этом говорит прямо, а образцы передают заголовок
строкой `proxy_pass_header Upgrade;`. Если конфиг вы писали сами, добавьте её
в блок `/ws` или уберите то, что чистит там заголовки ответа.

## Почему образы весят по-разному

Почти весь вес — базовый образ PHP, наша часть добавляет к нему около тридцати
мегабайт. Под одной и той же меткой `php:8.3-apache` в разное время лежат разные
сборки, и разница между ними доходит до двухсот мегабайт. Поэтому сравнивать
размеры с чужой машиной бессмысленно, пока не совпал дайджест базы:

    docker image inspect php:8.3-apache --format '{{index .RepoDigests 0}}'
    docker history <образ>     # послойно: видно, что наши слои весят копейки

Метку намеренно не прибиваем к дайджесту: обновления безопасности в базовом
образе важнее воспроизводимости размера до байта.

## Резервная копия

    docker compose exec db mariadb-dump -u root -p"$DB_ROOT_PASS" entrixy > backup.sql

Ключи в базе лежат зашифрованными: сервер их не читает и при переносе на другую
машину расшифровывать ничего не нужно.
